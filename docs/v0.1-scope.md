# BCOS v0.1 — Scope

> **BCOS는 protocol-first다.** 이 문서가 정의하는 CLI 명령은
> [RFC-001 Core](rfcs/RFC-001-task-protocol.md) 프로토콜 `0.1`(Experimental)의
> **첫 번째 구현체**일 뿐이다.
>
> **RFC-001 승인 전까지 구현에 착수하지 않는다.**

## 0. 한 문장 목표

> **manager가 쓴 Task 명세 하나만으로 worker가 이탈 없이 구현하고,
> 독립 reviewer가 승인하고, 그 전 과정이 Git에 감사 가능하게 남는다** — 를 최소 1회 성공시킨다.

v0.1은 자동화 도구가 아니라 **규율 도구**다. 사람이 루프 안에 있다.

**Worker 운용: Sequential Single Worker.**
`IN_PROGRESS` Task 1개, Worker 세션 1개, 수동 전달.
역할별 Task Template(backend·frontend·test 등)은 **v0.2이며 지금 만들지 않는다**
([ADR-003](decisions/ADR-003-task-centric-workers.md), [로드맵](vision.md)).

## 1. 포함 — CLI 명령

### 프로젝트

| 명령 | 동작 |
|---|---|
| `bcos init` | `.bcos/` 구조와 초기 파일 생성. 이미 있으면 **덮어쓰지 않고 종료(exit 1)** |
| `bcos status` | 현재 Task, 상태별 개수, 브랜치 표시 |
| `bcos reindex` | `tasks/*.md`를 스캔해 `state.json` 재생성 |

`bcos init`이 생성하는 것: `.bcos/{tasks,reports,reviews}/`, `state.json`, `events.jsonl`.
`CLAUDE.md` / `AGENTS.md`가 없으면 템플릿 생성, 있으면 건드리지 않는다.

### Task 조회

| 명령 | 동작 |
|---|---|
| `bcos task create --title <t> --slug <s>` | 다음 번호 자동 부여, 6개 필수 섹션 템플릿 생성, `TASK_CREATED` |
| `bcos task list [--status <S>]` | ID·상태·제목을 ID 순으로 한 줄씩 |
| `bcos task show <id>` | **worker용 최소 Context Package 출력** (§2) |

### Task 상태 전이

`bcos task start` · `submit` · `approve` · `request-changes` · `block` · `unblock`

**전이·허용 role·가드 조건은 [RFC-001 §1](rfcs/RFC-001-task-protocol.md)이 정의한다.**
여기 옮겨 적지 않는다. 이 문서는 명령 표면만 정한다.

모든 명령은 `--actor-role`과 `--actor-id`를 받는다. 기본값은 `human` / 호스트 사용자명.

> **가장 중요한 규칙:** `approve`를 수행하는 `actor_id`는 현재 attempt를 `submit`한
> `actor_id`와 달라야 한다. 구현한 주체가 완료를 선언할 수 있으면 BCOS의 가치는 0이다.

## 2. Context Package

`bcos task show`의 출력 구조와 제외 항목은 [RFC-001 §6](rfcs/RFC-001-task-protocol.md)에 있다.

크기 8,000자 초과는 **경고**이지 실패가 아니며, T-001 실행 후 실측값으로 재검토한다.

## 3. 데이터 모델

[RFC-001 §2–5](rfcs/RFC-001-task-protocol.md) 참조. 저장소 배치는 [architecture.md](architecture.md) §2–3.

## 4. 제외 — 명시적으로 만들지 않는 것

| 제외 항목 | 이유 |
|---|---|
| SQLite / `cache.sqlite` | Git 머지 불가. [ADR-002](decisions/ADR-002-storage.md) |
| Daemon | 호출할 대상이 없다 (BCOS는 LLM을 부르지 않는다) |
| MCP | v0.1 가치 검증에 불필요 |
| 자동 Agent 실행 | 비대화형 호출 가능 여부가 미검증 가정 |
| 병렬 Worker Pool | 동시 세션 관리 불가 |
| Worktree 자동화 | Windows 경로 길이 위험. v0.5 |
| Gemini / Cursor Adapter | 두 번째 사용처가 없다 |
| 자동 Merge · 배포 | Human-Controlled Autonomy 원칙 |
| 임베딩 메모리 검색 | API 비용 발생 → 비용 모델 위반. v0.1은 grep |
| 11단계 상태 머신 | v0.2 Review Loop와 함께 복원 |
| `bcos decision add` | ADR은 Memory의 하위 유형. 별도 명령 불필요 |

> **미래용 디렉터리나 인터페이스를 미리 만들지 않는다.**
> `adapters/`, `plugins/`, `IAgentAdapter` 같은 빈 껍데기를 만들지 않는다.
> 두 번째 사용처가 생길 때 만든다.

## 5. 완료 조건 (Definition of Done)

1. 모든 명령이 Windows PowerShell과 Git Bash 양쪽에서 동작한다.
2. `init → create → show → start → submit → approve` 전체 흐름이 통과한다.
3. `submit`은 Report 없이, `approve`는 Review 없이 각각 거부된다.
4. 제출한 `actor_id`가 `approve`를 시도하면 거부된다 (SoD).
5. `state.json`을 삭제해도 `bcos reindex`로 완전히 복원된다.
6. 모든 상태 변경이 `events.jsonl`에 남는다.
7. **worker가 `bcos task show` 출력만 받고 실제 Task 하나를 구현해낸다.**
8. 그 Task에서 worker가 읽은 파일 수를 기록했다. (측정 지표)

**7번과 8번이 진짜 검증이다.** 1~6번은 그것을 가능하게 하는 수단일 뿐이다.

## 6. v0.1이 실패했다고 판단하는 조건

- `bcos task show` 출력만으로 worker가 일하지 못하고 매번 저장소를 헤집는다
  → CLI가 아니라 **Task 포맷 설계**를 다시 만든다.
- 사람이 CLI를 우회해 `.bcos/`를 직접 고치는 편이 빠르다고 느낀다
  → 강제 규칙의 마찰이 가치보다 크다. 명령을 줄인다.

## 7. 다음 단계

v0.1 완료 후 실측값으로 **RFC-001의 `1.0` 승격 조건**(§10)을 평가한다.
그 전까지 새 RFC를 쓰지 않는다 — Memory Protocol은 실제 Report·Review가 쌓인 뒤 검토한다.
